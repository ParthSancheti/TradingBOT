Where a message actually travels

  Native: desktop/wa-direct.cjs messages.upsert -> desktop/main.cjs in-memory batch -> DesktopService.wa_sync -> Runner.accept_event_ts -> IntakePipeline.process.
  Extension: extension/scanner.mjs WPP/DOM -> background.js scan/observations -> Runner._handle -> IntakePipeline.process. Outgoing observations and LID mappings have a separate branch here.
  Local capture -> local worth/intent filter -> SQLite message / media / pending classification -> Runner.classify_pending -> GeminiClient.classify -> requests/offers or trusted Storehouse stock -> evaluate_inbound_trade -> find_best_stock_match -> calculate_dynamic_quote -> AI fact check or formatter -> working-hours decision -> outbound_queue or scheduled_jobs.
  Wake: DesktopService.run_scheduler_tick -> outbound_queue. Extension polls ready IDs, verifies target via actions.mjs and reports dispatch_result. Native triggerDirectPump separately claims, authorizes and calls WaDirectClient.sendDirect. Renderer reads activity, message/trace, alerts/list and outbound/list. An enqueued row, invoked send, provider acceptance, delivery and read are distinct events.
